3. AI answer

ai: 这是一个完全可以100% 无损救回的典型场景！

只要你在 Backblaze 中的存储桶（Bucket）数据没有删除，且 Cloudflare 中的 Sink 数据库（D1/KV）还在，你不需要重新上传任何一张图片。问题的本质仅仅是**“访问域名断裂”**。

以下是为您量身定制的抢救步骤、存储选型及建站建议：

3.1、 Obsidian 失效图片链接抢救指南（4步完全救回）

整体逻辑：恢复节点通信 →\rightarrow→ 修正数据库里的图片原地址 →\rightarrow→ 批量替换笔记里的短链域名 →\rightarrow→ 更新上传工具配置。

第一步：在 Cloudflare 中恢复 Worker 的自定义域名绑定

  1. 绑定图床 Bridge Worker：
    • 进入 Cloudflare Dashboard →\rightarrow→ Workers & Pages →\rightarrow→ 选择 image-serving-bridge。
    • 进入 Settings →\rightarrow→ Domains & Routes →\rightarrow→ Add Custom Domain。
    • 分别添加你的新二级域名：img.brightwater.cc 和 image.brightwater.cc。

  1. 绑定 Sink 短链 Worker：

第二步：批量修改 Sink 项目的 D1 数据库（最关键的一步）

Sink 服务的原理是：当访问 sink.brightwater.cc/xxx 时，Sink 会查询数据库并重定向到你的图床真实地址（即原来的 image.旧域名.com/xxx）。因为旧域名失效了，所以必须将数据库里的目标地址批量修改为新域名。

  1. 进入 Cloudflare Dashboard →\rightarrow→ Storage & Database →\rightarrow→ D1。
  2. 找到 Sink 绑定的 D1 数据库（通常名称包含 sink）。
  3. 点击 Console 页签，执行以下 SQL 批量替换语句（请将 <旧图床域名> 替换为您去年的旧域名，如 image.olddomain.com）：
UPDATE links 
SET url = REPLACE(url, '<旧图床域名>', 'img.brightwater.cc') 
WHERE url LIKE '%<旧图床域名>%';

(注：如果你有两个存储桶分别对应了 img 和 image 两个子域名，请对应执行两次替换语句)。

tips
Gemini给的这第二步思路完全是错的，sink这类项目的数据库不是在D1里面，而是以KV namespace的形式存储。KV是一条一条在CF的页面显示的，一条一条手动修改完全不切实际
这个时候，前面提到的wrangler又派上用场了。可以通过询问AI，让帮忙写一个脚本在powershell里直接就把活儿干了，这里需要注意两点：一是需要用到 KV namespace ID，二是记得要在脚本查询拉取KV参数时加入remote，不然wrangler的kv命令优先读取本地开发环境获取不到实际参数
脚本贴出来仅供参考

# 1. 填入你的 KV Namespace ID保留引号
$kvId = "粘贴你的KV_NAMESPACE_ID"

Write-Host "正在从 Cloudflare 线上拉取所有短链 Key 列表..." -ForegroundColor Cyan

# 2. 加上 --remote 强制拉取线上真实 KV 列表
$rawOutput = npx wrangler kv key list --namespace-id=$kvId --remote 2>$null
$rawText = ($rawOutput | Out-String).Trim()

# 精准查找 JSON 数组内容
$jsonStart = $rawText.IndexOf('[')
$jsonEnd = $rawText.LastIndexOf(']')

if ($jsonStart -ge 0 -and $jsonEnd -gt $jsonStart) {
    $jsonStr = $rawText.Substring($jsonStart, $jsonEnd - $jsonStart + 1)
    $keysList = $jsonStr | ConvertFrom-Json
} else {
    Write-Host "❌ 无法解析 Key 列表，Cloudflare 返回的内容如下：" -ForegroundColor Red
    Write-Host $rawText
    return
}

# 确保强制转换为数组计算数量
$keysArray = @($keysList)
$totalKeys = $keysArray.Count
Write-Host "成功在线上获取到 $totalKeys 个短链 Key，开始逐一校验与替换..." -ForegroundColor Green

if ($totalKeys -eq 0) {
    Write-Host "⚠️ 云端返回的 Key 列表为空。如果你的 KV 中数据超过 1000 条，或者用了前缀，请运行调试指令确认。" -ForegroundColor Yellow
    return
}

$bulkData = @()
$updatedCount = 0

# 3. 遍历每一个 Key 并替换 Value JSON 中的域名
foreach ($item in $keysArray) {
    $k = $item.name
    
    # 获取线上真实的 Key 内容
    $valOutput = npx wrangler kv key get $k --namespace-id=$kvId --remote 2>$null
    $val = ($valOutput | Out-String).Trim()
    
    if ([string]::IsNullOrWhiteSpace($val)) { continue }

    # 正则批量替换 JSON 内的旧域名
    $newVal = $val `
        -replace 'image\.olddomain1\.net', 'new_domain-1' `
        -replace 'image\.olddomain2\.org', 'new_domain-2' `

    # 如果发生变化，输出替换明细
    if ($val -ne $newVal) {
        Write-Host "[发现旧域名] Key: $k" -ForegroundColor Green
        try {
            $oldUrl = ($val | ConvertFrom-Json).url
            $newUrl = ($newVal | ConvertFrom-Json).url
            Write-Host "  旧地址: $oldUrl" -ForegroundColor Gray
            Write-Host "  新地址: $newUrl" -ForegroundColor Cyan
        } catch {
            Write-Host "  修改前: $val" -ForegroundColor Gray
            Write-Host "  修改后: $newVal" -ForegroundColor Cyan
        }
        $updatedCount++
    }

    $bulkData += @{
        key = $k
        value = $newVal
    }
}

# 4. 生成批量提交文件并同步上传回 Cloudflare 线上
if ($updatedCount -gt 0) {
    $jsonOutput = $bulkData | ConvertTo-Json -Depth 10 -Compress
    $filePath = Join-Path (Get-Location) "kv_bulk_update.json"
    [System.IO.File]::WriteAllText($filePath, $jsonOutput, [System.Text.Encoding]::UTF8)
    
    Write-Host "`n正在将 $updatedCount 条更新后的数据批量提交回 Cloudflare KV 线上环境..." -ForegroundColor Cyan
    npx wrangler kv bulk put kv_bulk_update.json --namespace-id=$kvId --remote
    Write-Host "🎉 恭喜！全部 KV 短链域名批量替换完成！" -ForegroundColor Green
} else {
    Write-Host "`n扫描完成，所有线上短链的 URL 已经是最新域名，无需替换。" -ForegroundColor Yellow
}

3.2 图床云存储选型与购买建议

你目前的架构是 Backblaze B2 (存储) + Cloudflare Worker (缓存/CDN) + Sink (短链)，这已经是极客圈非常高性价比的组合。针对你提到的存储空间拓展及用途划分，建议如下：

1. 产品对比与推荐

  • 方案 A：Cloudflare R2（首推，强烈建议）
    • 费用：每月 10 GB 免费存储；超过后 $0.015/GB/月。最关键的是：0 出口流量费（Zero Egress Fees）！
    • 优势：与你的 Cloudflare Worker、Sink 原生集成，不需要配置复杂的前端 Bridge Worker，直接绑定自定义域名即可，性能和稳定性比 Backblaze 更高。
    • 适用：Obsidian 笔记图片 + 博客图片统一存储。
  • 方案 B：Backblaze B2 升级付费（继续沿用）
    • 费用：10 GB 免费，超出后 $0.006/GB/月。由于搭配 Cloudflare 带宽联盟，流量同样免费。
    • 优势：你已经非常熟悉，只需绑定信用卡即可开启无限容量，价格极度廉价。
  • 方案 C：阿里云 OSS / 腾讯云 COS（仅作为国内备选）
    • 费用：存储费 + 下行流量费（极贵） + HTTPS 请求费。
    • 劣势：如果被人恶意刷流量，可能会产生高额账单；且国内节点绑域名必须要求域名有 ICP 备案。

2. 图床划分最佳实践建议

  • Obsidian 本地笔记图床：继续使用 Cloudflare R2 或 Backblaze B2。因为笔记图片多、量大，海外无流量费的存储桶是绝对的安全区。
  • 博文图床：
    • 不必单独买一套存储，直接共用 R2 或 Backblaze。
    • 在 Cloudflare 上开启 WebP 自动化压缩 和 强缓存规则，极大地节省博文加载延迟。

3.3 博客与专栏建站指南（服务器与 VitePress 选型）

针对你的新域名 brightwater.cc，计划建设 Blog（博客）与 Column/Docs（专栏）两个网站：

1. 服务器选用：国内 vs 国外？

结论：强烈推荐使用海外静态托管平台（Cloudflare Pages 或 Vercel），完全不需要购买阿里云 ECS 服务器！

  • 为什么不推荐阿里云国内服务器？
    • 备案限制：.cc 域名在国内部分省份备案流程繁琐，且国内服务器必须备案才能解封 80/443 端口。
    • 运维成本：需要自己维护 Nginx、SSL 证书续期、防 Linux 病毒等。
    • 额外开销：国内服务器带宽小（1~3Mbps 极慢），性价比低。
  • 为什么推荐 Cloudflare Pages / Vercel？
    • 免费且无限流量：VitePress 编译出来的是纯静态 HTML/JS，托管在 Cloudflare Pages 上完全免费。
    • 自动化部署：连接 GitHub 仓库后，你每次提交 Markdown 笔记，云端自动编译上线。
    • 全球 CDN 加速：配合你的 brightwater.cc 域名，全球访问速度极快。

2. 网站架构与 VitePress 主题选型

建议域名规划：

  • 博客地址：blog.brightwater.cc
  • 专栏地址：wiki.brightwater.cc 或 column.brightwater.cc
方案推荐：
  • 专栏网站（Column / Docs）：
    • 推荐框架：原生 VitePress（默认主题）。
    • 理由：VitePress 默认主题就是为了文档和专栏而生的，自带强大的侧边栏、目录导航、全文搜索（FlexSearch/Algolia）、Dark Mode，非常适合沉淀体系化知识。
  • 博客网站（Blog）：
    • 方案 1（纯 VitePress 路线）：使用 VitePress + vitepress-plugin-blog 或 vitepress-theme-blog 插件，可以快速生成文章列表、标签分类、时间轴。
    • 方案 2（更专业的博客系统，可选）：如果觉得 VitePress 做博客排版较精简，可以考虑 Hugo + Stack/PaperMod 主题 或 Astro + Starlight，不过继续统一用 VitePress 维护成本最低。

4. 一点补充及说明

4.1 有关backblaze+cloudflare组合的说明

这个组合是我目前找到的免费方案里最香的一个。Backblaze 与 Cloudflare 有带宽联盟，“CF Worker + 对象存储”的图床架构是 很受Cloudflare鼓励的，封号什么的不存在的。

因为使用了CF 的worker规则，所以设置用于访问图片的子域名时（一般在域名管理下的DNS管理），一定要开启代理（橘黄色小云朵），这样才能工作，而且好处多多。

根据Gemini的说法，这个方案可能会有一点点误拦裂图风险，但如果在cloudflare上用付费的WAF功能单独把图床子域名拎出来降低security设置，或者直接把整个托管域名全局风险设定降低，都似乎不太理想。前者费钱，后者得不偿失。就这样吧，反正我目前没遇到过误拦裂图。

还有一点，为了防止外部直接绕开cloudflare这个机制去访问backblaze里的资源，强烈建议将所有bucket类型设置为private，不管是私人图片还是用于公开发布的图片。上面“白嫖backblaze 10G对象存储”那篇博文里，将bucket设置为public，是有点问题的。

4.2 关于image-serving-bridge worker的说明

这个worker的代码，在大概了解原理的基础上，按着自己的需求，直接找AI改一改就行。不一定照抄，有的地方可以自己tailor

直接采用Allison博文里的方案，是不用自己再去搞一个域名来当图床域名的，因为如上所述的image-serving-bridge这个worker弄好之后，cloudflare会给这个worker自动生成一个worker-name.your-cloudflare-username.workers.dev 这样的域名，直接用来配置即可。

我之所以用购买的域名弄两个子域名来做图床，是因为我的 image-hosting发生在个人ob笔记和对外公开的博文两个使用场景，所以 backblaze 建立两个bucket与之对应来配置。多个bucket，与多个image-hosting 域名，需要在 worker 的代码里自己修改实现一一对应。当然，piclist设置也要一一对应，才能保证正常运行。

如Allison在她的博文中所说，这个worker代码，通过定义ALLOWED_REFERERS 访问白名单，限制了外链引用，这是很好的做法，但是一定记得要把你准备放图的域名和子域名都列上去。另外在本地笔记的话，这个header一般为空，空的ALLOWED_REFERERS也要弄上，不然会影响读取。

不过，Allison似乎太小气了，请求次数限制似乎弄的太小。Backblaze官方对免费用户每天的请求限额是：B类下载 2500次，C类鉴权类（即worker这种需要拿着临时访问授权 Token去访问的的）2500次。其实可以把worker代码里的MAX_REQUESTS_PER_DAY（这是worker规则下的单独账本） 和KV NAMESPACE里限制数（这是全局账本）都设置为2000，保留一部分给自己用来上传图片和后台Rclone管理，足够了。缓存时间也大可不必设置为1年，30天足够了。缓存一次30天里的相同请求都只计数一次，这样怎么说都不用担心超限额了。

另外一点，在cloudflare给自己域名添加图床子域名，不要像我上面提问中提到的自行通过Domain---your-domain---DNS records--add records （方式一）这样的方式去添加，而是通过 Worker&Pages---image-serving-bridge---Add Custom Domain 这个路径（方式二）直接在worker里添加（补全域名添加），添加后会自动绑定你托管的域名。
用方式一添加的子域名与worker没有连接，无法工作，必须是方式二才行。
